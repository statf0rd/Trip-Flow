## 2. Принципы

1. **Честность и привязка к коду.** Каждое содержательное утверждение опирается на реальный код (file:line) или на реально полученный результат. Никаких правдоподобных, но непроверенных цифр.
2. **Реальные измерения (гл.4).** Числа берутся из прогона существующих JVM-тестов и новых измерительных харнессов, а не выдумываются. Аппаратно-зависимое (дальность/переподключение Bluetooth, геошаринг) описывается как методика наблюдений, без подложных метрик.
3. **Единый стиль.** Формальный научный русский, как в гл.1–2. Гибрид показа кода: проза + короткие листинги Kotlin + формулы + новые TikZ-схемы. Сквозная нумерация Рис./Табл.
4. **/humanizer.** Каждая глава после черновика прогоняется через humanizer (убрать признаки ИИ-текста: инфляцию, «правило трёх», лишние тире, шаблонные обороты) до вшивки в `ВКР.md`.
5. **Без расширения функциональности приложения** (по решению пользователя): расхождения «требование ↔ код» закрываются выравниванием текста, а не доработкой кода.

## 3. Правки честности в главе 1 (минимальные, согласованы)

Эти расхождения найдены при чтении кода и должны быть устранены, иначе на защите они уязвимы.

### 3.1. F5 и критерий качества маршрута (§1.4)

Код (`NearestNeighborRouteOptimizer`, [RouteOptimizer.kt:159,389,419](app/src/main/java/com/triloo/data/route/RouteOptimizer.kt)):
- порядок строится жадным «ближайшим соседом» по **геодезическому расстоянию (формула гаверсинусов)**;
- фиксируется **только старт** (ближайшая точка к `startLocation`, иначе `places.first()`); конечная точка не фиксируется;
- реальные дорожные дистанции из маршрутных API (Yandex MapKit [9], OpenRouteService [17]) используются в `calculateRoute()` для **итоговой визуализации и метрик** (длина, время, полилиния), но НЕ в самом упорядочивании.

Правки текста:
- **F5** (строка ~560): убрать «с фиксацией стартовой и конечной точки» → «с фиксацией стартовой точки»; «поверх реальных дистанций из маршрутных API» → «по геодезическим расстояниям (формула гаверсинусов); реальные дорожные дистанции из маршрутных API используются для построения и оценки итогового маршрута».
- **Критерий «Качество маршрута на выходе оптимизатора»** (§1.4, строка ~608): «поверх реальных дистанций из маршрутного API» → «по геодезическим расстояниям»; формулировку отклонения 25–40% сохранить, но привязать к измеренным значениям из §4.3.

### 3.2. F8 — режимы сплита (§1.4)

Код (`buildSplits`, [ExpenseRepository.kt:141](app/src/main/java/com/triloo/data/repository/ExpenseRepository.kt:141)): реально считаются `PAYER_ONLY` (без сплита), `EQUAL`, `EXACT`; `PERCENTAGE` и `SHARES` объявлены в enum `SplitType`, но возвращают пустой список (`else -> emptyList()`).

Правка текста:
- **F8** (строка ~563): «разбиение расхода в режимах PAYER_ONLY, EQUAL, EXACT, PERCENTAGE, SHARES» → «разбиение расхода в режимах PAYER_ONLY, EQUAL и EXACT (режимы PERCENTAGE и SHARES предусмотрены моделью данных и отнесены к дальнейшему развитию)». В гл.3 §3.2 описать 3 рабочих режима, остальные два — как заявленные.

Других правок гл.1/гл.2 не вносим.

## 4. Глава 3 — структура и содержание

Вводный абзац: связь с гл.2 (архитектура спроектирована, здесь — реализация алгоритмов), карта подсистем.

### §3.1. Эвристическая оптимизация порядка обхода точек
- Постановка: упорядочивание точек дня — открытая задача коммивояжёра, NP-трудная [13]; оправдание эвристики ближайшего соседа [4, 5].
- Алгоритм: жадный NN, старт фиксирован; формула гаверсинусов (привести как формулу LaTeX). Сложность O(n²).
- **Листинг 1**: метод `nearestNeighbor` ([RouteOptimizer.kt:389](app/src/main/java/com/triloo/data/route/RouteOptimizer.kt:389)) (сокращённо).
- Двухуровневость: упорядочивание по геодезии (офлайн-устойчиво, без сети), реальные дорожные дистанции/время — на итоговую отрисовку через `calculateRoute` (Yandex [9]/ORS [17]/гаверсинус как резерв). Интерфейсы `RouteOptimizer`/`MapRouteProvider`/`NearbyPlacesProvider`, DI `RouteModule`.
- `RoutePlanningAssistant`: распределение по дням + эвристический выбор режима передвижения по суммарной дистанции.
- **Рис. 8** (новый TikZ): геометрия обхода — исходный порядок против NN на наборе точек.

### §3.2. Мультивалютный расчёт балансов и упрощение долгов
- Хранение валюты в `Expense` (`amount`, `currency`, `amountInBaseCurrency`, `exchangeRate`, `exchangeRateDate`). Конвертация: кэш `CurrencyRate` + ExchangeRate-API; устаревание `RATE_MAX_AGE_MS=24ч` ([ExpenseRepository.kt:323,343](app/src/main/java/com/triloo/data/repository/ExpenseRepository.kt:323)); предупреждение при устаревании (N7).
- Режимы сплита (3 рабочих) — **Табл. 5** (режим → формула доли). `createEqualSplits`/`createExactSplits`.
- Чистый баланс участника: формула (плательщик −сумма; должники +доля), `calculateBalances` ([:169](app/src/main/java/com/triloo/data/repository/ExpenseRepository.kt:169)). Исключение `isSettled` и `PAYER_ONLY`.
- Упрощение долгов: жадный «максимальный должник ↔ максимальный кредитор», BigDecimal, порог 0.01, округление HALF_UP. **Листинг 2**: `simplifyDebts` ([:199](app/src/main/java/com/triloo/data/repository/ExpenseRepository.kt:199)). Свойство: число переводов ≤ n−1; не гарантирует глобальный минимум, но близко и быстро.
- **Рис. 9** (новый TikZ): пример — балансы трёх участников → минимальный набор переводов.

### §3.3. Протокол обмена Triloo Relay
- Транспорт: Bluetooth Classic RFCOMM, сервисный UUID `4cf14d9b-…`, асимметрия (хост — RFCOMM-клиент, гость — сервер). Кадрирование: сигнатура `TRILOO_BT`, версия протокола 7, длина-префикс для `PACKAGE`.
- Рукопожатие `INTENT → CONSENT → PACKAGE → RESPONSE`, статусы `APPLIED/DUPLICATE/FAILED` (опираемся на Рис.6/7 из гл.2, без дублирования схем; шаги — по коду `BluetoothRelayManager`).
- Шифрование: `AES/GCM/NoPadding`, ключ = SHA-256(общий секрет), IV 12 байт (`SecureRandom`), тег 128 бит, формат IV‖ciphertext‖tag. **Листинг 3**: `RelayEncryption.encrypt/decrypt` ([RelayEncryption.kt](app/src/main/java/com/triloo/data/relay/RelayEncryption.kt)). NIST SP 800-38D [6].
  - ⚠️ Проверить при написании: что фактически подаётся как общий секрет — `tripId` (как сказано в гл.2) или invite-код (как в doc-комментарии `RelayEncryption`). Текст привести в соответствие с реальным вызовом в `BluetoothRelayManager`.
- Слияние: LWW по `updatedAt` (insert / replace-if-newer / drop), защищённое удаление по `DeletionLog` (удалять только если `entity.updatedAt ≤ deletion.deletedAt`), сброс старых удалений при реинсерте. **Листинг 4** (правило upsert/удаления, сокращённо).
- Идемпотентность в два уровня: LWW делает повтор безвредным; `RelaySyncMetadataRepository` хранит applied-`packageId` (до 50) → повтор = `DUPLICATE`.
- Дельта-обмен: `buildPackage(tripId, sinceCursor)` фильтрует по курсору; `isDelta/baseCursor/changeCursor` — реализовано.

### §3.4. Онлайн-синхронизация с backend
- `OnlineSyncRepository` ([data/sync/OnlineSyncRepository.kt](app/src/main/java/com/triloo/data/sync/OnlineSyncRepository.kt)) переиспользует `buildPackage/encodePackage/decodePackage/mergePackage` из `RelayRepository` — **подтверждённый элемент новизны** «единый доменный слой, транспорт сменяемый» (push/pull поверх HTTPS вместо Bluetooth, та же LWW + DeletionLog).
- Эндпоинты `POST /api/v1/sync/push`, `GET /api/v1/sync/pull` ([OnlineSyncApi.kt](app/src/main/java/com/triloo/data/remote/OnlineSyncApi.kt)); формы запроса/ответа; курсор `since`.
- Авторизация Bearer-токеном; ролевой контроль на сервере (`server/src/routes/sync.js`): MEMBER синхронизирует только расходы, ADMIN не передаёт владение, создавать снапшот может OWNER/ADMIN.
- **Честность о зрелости:** push/pull и ролевые проверки реализованы и работают end-to-end (сервер развёрнут через pm2), но: нет интеграционных тестов, email-верификация отключена флагом, нет веб-панели. В тексте — «реализована и развёрнута базовая онлайн-синхронизация с ролевым контролем; промышленная закалка (тесты, верификация, мониторинг) — за рамками работы». Не переоцениваем и не занижаем.
- Опц. **Рис. 10** (sequence push/pull) — добавить, только если усиливает; иначе ограничиться прозой.

### §4.4. Корректность слияния пакетов Triloo Relay
Прогон `RelayRepositoryTest` (LWW-keeps-newer, deletion+insert/no-resurrection, delta-by-cursor) + **новые проверки**: идемпотентность (двойное `mergePackage` → второй прогон 0 изменений, число строк неизменно), повтор `packageId` → `DUPLICATE`. **Табл. 8**: сценарий → ожидание → результат.

### §4.5. Безопасность канала Triloo Relay
**Новый тест** `RelayEncryptionTest` (чистый JVM): round-trip; неверный секрет → отказ; искажение 1 байта шифртекста → исключение по тегу GCM (`AEADBadTagException`); разные IV при повторном шифровании одного текста. Привязка к критерию безопасности §1.4 и [6].
